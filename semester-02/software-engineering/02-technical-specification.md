# Техническое задание — система расписания

## 1. Назначение

Разработать локальное настольное приложение для просмотра студентом расписания своей группы. Предусмотреть интерфейс редактора для управления занятиями. Система должна запускаться из IDE и не зависеть от постоянного подключения к Интернету.

## 2. Пользовательские роли

- Студент: вход, выбор дня, просмотр своих занятий, выход.
- Редактор: вход, просмотр расписания групп, создание, изменение и удаление занятия.

Роли описывают планируемый функционал. Интеграция с внешними системами не входит в MVP.

## 3. Функциональные требования

| ID | Требование |
|---|---|
| F01 | Авторизация по логину и паролю, сообщение при неверных данных |
| F02 | Определение студенческой группы и роли по аккаунту |
| F03 | Просмотр расписания выбранного дня: время, предмет, преподаватель, аудитория |
| F04 | Сортировка занятий по времени; сообщение при отсутствии занятий |
| F05 | Редактор может добавлять и изменять записи |
| F06 | Проверка даты, времени, группы, аудитории и пересечений |
| F07 | Удаление занятия после подтверждения |
| F08 | Сохранение данных в локальной БД; повторная загрузка после перезапуска |
| F09 | Выход из аккаунта; студент не может изменять расписание |

## 4. Данные

- User: id, login, passwordHash, salt, role.
- Student: id, userId, name, groupId.
- Group: id, name.
- Lesson: id, title, teacher.
- ScheduleEntry: id, groupId, lessonId, date, startTime, endTime, room.

Одна группа содержит много студентов и занятий; один предмет используется в нескольких записях расписания. Уникальны логин и код группы. Начало занятия раньше окончания. При конфликте времени группы или аудитории запись не сохраняется.

## 5. Технические требования

Java 17+, JavaFX, SQLite/JDBC. Разделить интерфейс, модель, сервисы и слой хранения. Пароль хранить в виде хеша с индивидуальной солью, например PBKDF2. Валидацию ролей и конфликтов проводить в сервисе, а не только в интерфейсе. Доступ к БД выполнять параметризованными запросами.

Локальные ошибки хранилища обрабатываются сообщением без потери ранее сохранённых данных. Интерфейс должен поддерживать клавиатуру и иметь понятные поля. Целевое время отображения расписания для 1000 записей — не более 2 секунд на компьютере разработчика (проверяется после реализации).

## 6. Критерии приёмки

1. Студент с корректными данными открывает расписание своей группы.
2. Выбор дня меняет список; пустой день имеет понятное сообщение.
3. Редактор сохраняет корректную запись, которая остаётся после перезапуска.
4. Пересечение времени группы или аудитории отклоняется.
5. Неавторизованная операция редактирования отклоняется.
6. Выход возвращает пользователя на экран входа.

## 7. Границы проекта

Не включены онлайн-синхронизация, push-уведомления, автоматическое построение расписания, интеграция со студенческим порталом. Реализация запланирована отдельно.
